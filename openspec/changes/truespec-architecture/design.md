# TrueSpec — architecture design

## Context

Planning is closed (`product-management/planning-close.md`, 2026-10-06) and six implementation plans were written from real screens (2026-10-08). This design turns that material into one architecture the build follows. The product: a public showroom plus a single-owner office for a Nigerian vehicle-import business, with one invariant above all others — **what the owner paid never reaches the browser**. The reference screens live in `test-truespec-v2` (outside this repo); this change builds the real thing in this repo.

Stack as ruled, revised 2026-10-08 by owner decision: Next.js + TypeScript, **Neon** (Postgres), **Clerk** (auth and sessions), **Sanity** (images *and* enquiry PDFs), Vercel hosting. Supabase is dropped — its free tier caps accounts at 2 projects, which TrueSpec cannot fit under (owner ruling 2026-10-08); the same ruling placed enquiry PDFs in Sanity. Rulings referenced by code (C1–C4, A1–A7, F1–F6, R1–R3; R3 is superseded by the owner's 2026-10-12 rate removal — see D5) are recorded in `product-management/planning-close.md` and restated as requirements in this change's specs.

## Goals / Non-Goals

**Goals:**

- One repo where the contract (specs), the how (this design), and the work list (tasks) live together, so the Builder and the tester work from requirements, not from prose archaeology.
- The cost-leak invariant enforced structurally (one allow-list serializer), with a check that must pass before handover.
- Money figures that are provably identical everywhere: integer minor units, one exact totals function, no exchange rate anywhere.
- Free-tier survivability: sessions, abuse control, and job scheduling enforced by the app, not by paid features of any vendor.

**Non-Goals:**

- Staff roles, multi-admin, or public accounts — v1 is one owner.
- Image derivative pipeline (F3) — originals with a size cap; Sanity CDN params are the upgrade path.
- In-app password reset (F2) — recovery is a documented operation at the identity provider.
- Any CryptoPilot work — a different product, not part of this architecture.
- Editing `product-management/` — it stays as the readable record; disagreements resolve in favour of ruling dates and this change's specs.

## Decisions

### D1 — Next.js App Router with Server Components as the render model
**Decision:** One Next.js + TypeScript app; showroom pages are server-rendered; office pages are server-rendered behind a session check.
**Why:** The product design already picked Next.js + TypeScript ("one language throughout"). Server rendering means the allow-list serializer is the only path to the browser — no client-side fetch of raw rows to leak.
**Alternatives:** Static-site + API (rejected: the boundary would live in two places); separate SPA + backend (rejected: doubles the surface where costs could escape).

### D2 — The boundary is an allow-list serializer, not database permissions
**Decision:** Public data is produced by exactly one mapping function with an explicit field allow-list; the database is reachable only server-side via a server-only connection (the Neon connection string never reaches the browser); RLS stays restrictive but is explicitly *not* the mechanism (product-design §A, data-model D5).
**Why:** One function is one place to audit and one place to test. A browser that never holds credentials can't be tricked into a cost query. RLS-as-boundary fails open if a key ever leaks; the allow-list fails closed — fields simply aren't in the map.
**Alternatives:** RLS-only (rejected — documented as non-mechanism in D5); field-level views per screen (rejected — N surfaces, N chances to drift).

### D3 — Server Actions for every office write
**Decision:** All office state changes go through Server Actions (automatic origin check, POST-only); Route Handlers are reserved for reads and webhooks, and any write that must be a Route Handler carries an explicit origin check (system-model item 8).
**Why:** CSRF safety comes from the framework's default on the common path instead of a check someone must remember per endpoint.
**Alternatives:** Route Handlers everywhere (rejected — origin check becomes manual and forgettable).

### D4 — Clerk carries the sign-in; the app enforces every session rule (C1, C2; revised 2026-10-14)
**Decision:** Clerk is the identity provider: it holds the account, the credential, the sign-in and the provider session cookie, and its own sign-in is mounted in the office. The application builds no password form, stores no credential material and **never sees an attempt**, so per-attempt rules are Clerk's: account lockout after **10 failed attempts** for a **bounded period that clears itself** (owner ruling 2026-10-14 — ten attempts, thirty minutes, never indefinite and never needing support to clear), Clerk's per-address rate limits left in force, and **bulk** user-enumeration protection on. Clerk's application is in **invite-only** access mode, which is what makes "exactly one account, no public sign-up" true; the owner creates his one account himself. The app keeps its own `session` row per provider session (`created_at`, `last_seen_at`, `expires_at = created_at + 7 d`) so both lifetime limits stay app-enforced: valid iff `now < expires_at` and idle ≤ 12 h, with `last_seen_at` refreshed on a 5-minute cooldown. Every office page and data request is verified against that row on the server. Sign-out revokes the provider session and our row together.
**Why:** Clerk's 7-day maximum lifetime is its free default, but its inactivity timeout is a paid feature — so the 12-hour idle rule must live in our table anyway (the spec demands enforcement regardless of any provider's plan tier), and once the table exists the 7-day cap is enforced there too. The owner ruled on 2026-10-14 that **Clerk carries the sign-in, not the office**, superseding the earlier design in which the app's own form posted to our route and applied the failure rules before forwarding the attempt: that design needed the attempt to pass through our server, which a provider-carried sign-in never does. The abuse requirement it existed for is now met by the provider's own bounded lockout and rate limits, checked against Clerk's documentation the same day (lockout configurable, minimum five attempts, bounded duration; per-address rate limits on the sign-in API; bulk enumeration protection). Invite-only is free, whereas the allowlist — the other way to reach "exactly one account" — needs a paid plan in production.
**Alternatives:** the app's own form posting to a server-side route that applied the delay schedule and per-IP window before forwarding (superseded by the owner's 2026-10-14 ruling — it required credential handling in our code and a path Clerk's component does not take); Clerk's **strict** enumeration protection (rejected — it forbids password as the starting strategy, which would cost email-and-password sign-in; the concealment limit is recorded in the spec); Clerk's allowlist instead of invite-only (rejected — paid plan in production); Clerk paid inactivity timeout (rejected — depends on a paid plan tier); self-managed password hashes in our own table (rejected — Clerk owns credentials, and F2 recovery then lives at the provider); JWT-only (rejected — no revocation on sign-out).
**Settled (owner ruling 2026-10-14, recorded as D20):** the application no longer sees failed attempts, so `auth_attempt`'s original purpose — a row per attempt, written by the app — no longer holds; the table is nevertheless **kept exactly as it is**. It is now a **harmless no-op** — the app writes no attempt row, because a provider-carried sign-in never passes through our server — and the daily job's 90-day retention rule built on it (D8) survives unchanged. Removing it was weighed and declined: it would cost a forward-only migration plus edits to `specs/media` and TASK-006's plan, for no behaviour gained. What the app still knows is its own successful sign-ins — it creates the `session` row itself (D17).

### D5 — Money: integer kobo, no exchange rate, one totals function (owner ruling 2026-10-12; supersedes R3)
**Decision:** Every money column is `integer` (kobo) and every amount is naira; no exchange rate exists anywhere (not in Settings, not on a cost line, not on a car); total cost and profit are computed by a single function; nothing stores profit or totals — all are derived at read time.
**Why:** Floats drift; storing totals duplicates truth. The rate was removed by the owner (2026-10-12) and everything is naira — a cost paid in dollars is entered as its naira amount. The rate was never in the source spec (`demo_product.pdf`), only in the prototype screens, and mixing currencies in one total would cause trouble for no benefit.
**Alternatives:** Per-line rates (R3, 2026-10-08 — superseded 2026-10-12); global settings rate (rejected); `numeric` with scale (rejected — scale > 0 invites rounding in more than one place).

### D6 — **Revised 2026-10-14 by D15.** Sold is a primary state, and setting it performs the sale (30, system-model C/40)
**Decision (as revised):** **Sold is one of the four primary states** (D15), and **setting it is what performs the sale** — the state comes first and the action follows. The moment a car is set Sold, the sale is recorded (sale price and date), real profit is measured, and the car leaves the showroom and the stock counts. Un-setting it undoes that action: the car returns to its **previous primary state**, logged, and the sale row is reversed or voided. The **money facts stay on the sale row** — never folded into the state, never moved onto the car. Car states and enquiry states remain editable registry rows (deletion blocked while occupied), but the **four primary car states are fixed**; only the owner-made **secondary** states are his to add, rename or delete (D15).
**Why:** The owner's words (2026-10-14): *"sold is a state with an action … it is a state first, you set it, then an action occurs."* The earlier shape — a `car.sold` boolean held independent of `state_id` and explicitly *not* a state choice — could not express a world where every car sits under one of exactly four states. What that decision protected is kept: the money lives on the sale record, so reversal still reconstructs cleanly instead of resurrecting money.
**Alternatives:** Sold-as-state in the old shape (rejected at the time — reversal corrupts history; **overtaken by the owner's 2026-10-14 ruling**, and the force of that objection answered by keeping the money on the sale row); a plain boolean flag (rejected now — it cannot be reconciled with a mandatory four-state vocabulary); hard-coded enums (rejected — the owner must be able to add his own secondary states).

### D7 — Sanity for images and enquiry PDFs (A7, owner ruling 2026-10-08)
**Decision:** Car photos are Sanity assets behind the CDN, referenced by `car_photo.sanity_asset_id` (cover = position 0). Enquiry PDFs are also stored in Sanity — as file assets with randomized filenames under an `enquiry-pdfs` designation; the real filename and the asset reference live only in the database, and a reference never appears in any payload that leaves an authenticated office response. Upload-first, car-saves-second. Daily job reconciles by **reporting**: rows whose asset 404s and assets/PDFs of deleted records are surfaced to the owner as items waiting to be cleared, while an asset no record ever referenced (an abandoned upload) is the job's own litter and is cleared by it — settled with the owner 2026-10-13. **No Studio is built or deployed** (owner ruling 2026-10-13): Sanity's own starter guide offers one, and it was declined — the store is reached only by the application's server code through the API, the database remains the one place a record lives, and there is one deployment fewer to secure and watch. The dataset is public-read, since the showroom serves assets from the CDN.
**Why:** A7 restored the product-design stack; Sanity's CDN removes the single largest demo risk (image weight on mobile data) without writing image code. The owner ruled PDFs into Sanity as well (2026-10-08), keeping the stack at four vendors: Neon, Clerk, Sanity, Vercel — one asset store, one failure mode to monitor.
**Trade-off:** A Sanity asset URL is fetchable by anyone holding the exact reference — a randomized filename makes that reference unguessable (capability link, no expiry). The app's guarantee is that such references never appear outside an authenticated office response and are cleared when the owner clears their import — never by the system on its own. If strict expiry is ever required, the upgrade path is an expiring proxy route or a private dataset — recorded, not built in v1.

### D8 — Jobs: one Neon scheduled function, minimal surface
**Decision:** One daily job — a **Neon scheduled function** (Function Trigger, five-field UTC cron; available on the free tier and fires even when compute has scaled to zero) — that **reports rather than deletes**: the drift report (deleted records whose files remain, rows pointing at a missing asset, dead PDFs), the retention notice for enquiries (A4 — it only flags what is due for the owner's decision), and a backup heartbeat. Its only removals are its own litter, both settled with the owner (2026-10-13): assets that no record ever referenced (abandoned uploads) and `auth_attempt` rows past 90 days. Nothing belonging to a record is ever removed by the job — no tombstone hard-delete, no pruning of a record's files, no automatic deletion of his data. Vercel Cron (Hobby allows one run per day) is the documented fallback carrier. Monitoring = uptime check + in-office `last_backup_at` — no mail channel in v1.
**Why:** All deferred cleanup shares one cadence; batching daily is plenty for a single-owner product and stays inside free-tier call budgets. A scheduled function beats in-database `pg_cron`, which only runs while compute is awake — on Neon's free tier scale-to-zero cannot be disabled, so `pg_cron` would silently miss runs whenever the database slept.
**Alternative:** Vercel Cron daily trigger (kept as documented fallback — one run per day is all this needs); per-concern jobs (rejected — more triggers, more quota churn, same outcome). The function is declared in the repo's committed `neon.ts` policy (Neon config-as-code) and applied with `neon deploy`, so the job's carrier is versioned and reviewed with the code — set up 2026-10-08 against the owner's linked project.

### D9 — Rendering the office per device (UI plan)
**Decision:** Phone/tablet/laptop are widths, not designs: edit-as-full-page/drawer/inline, state changes via bottom sheet/sheet/inline dropdown, filtering full-screen sheet/sheet/bar dropdown. Dark is default with a persisted visitor toggle; one shared token set for both sides.
**Why:** Adopted UI-plan answers (95 questions, rulings 2026-10-06); recorded here so the build doesn't re-open them.

### D10 — Seed and migrations split (D6 of data-model plan)
**Decision:** Base state rows (four car groups, five enquiry states) live in migrations as built-in contract; demo cars live in an idempotent first-run seed.
**Why:** Migrations survive re-seeding; demo data must be re-runnable without duplicating registry rows.

### D11 — An enquiry is not a car record (owner ruling 2026-10-13)
**Decision:** `enquiry` holds the customer (name, number), the car asked about **in the customer's own words** as free text, a note, its state, its imported PDF and its dates — and holds **no reference to a car**: no `car_ref`, no car key. Taps and activity rows still join to a car by its `TS-####` reference, because a tap is a statement about a car the showroom holds; an enquiry is what a customer wants, which need not be a car we have and may be several cars at once. Each side carries its own identity and its own change-check.
**Why:** A customer asks for a car that is often not in the inventory. A join would force a car row to be invented for something we do not hold, or stand empty in exactly the normal case — and it fuses two records the business keeps apart (car tracking and customer tracking). Two customers asking for the same car are simply two enquiries.
**Alternatives:** Join by `car_ref` (rejected — the store's current shape and the join clause in `specs/inventory`; wrong whenever the car asked for is not held); a nullable car key (rejected — the link is empty precisely when the enquiry is real); creating a car row on demand (rejected — invents inventory the owner never entered).

### D12 — States are labels, not stages (owner ruling 2026-10-13)
**Decision:** Car states and enquiry states are **labels the owner attaches to track a record** — nothing more. No state requires another to come first, no transition is enforced or implied, and no part of the system may assume a flow: no "only New may reach Talking", no stage engine, no progress bar. An enquiry may be given Sold the same day it arrives; a car may be given any of its states at any time. Adding, renaming, reordering and deleting states is the owner's (deletion blocked while occupied), exactly as the registries already require.
**Why:** The owner's words — "there is no pipeline". A customer can enquire and buy immediately, so no stage model fits; a car's states exist because circumstances differ, not because a car must travel through them in order. A flow would be a rule nobody asked for, and since the states are data the owner edits, a flow baked into code would break the moment he changed them.
**Alternatives:** A board with allowed transitions / a pipeline model (rejected — scope creep, and contradicted by the owner); a fixed enum of stages (rejected — D6 already makes states data). The board view itself stays: it is a way of *showing* the states, and dragging a card sets a state — it implies no order.

### D13 — An upload lands as a draft, not a record (owner ruling 2026-10-14)
**Decision:** A file uploaded to create records is read, and the values it carries are written into a **draft** — a row in a holding place of its own, and never a `car` or an `enquiry` row. A batch produces one draft per record the file holds. The owner adds the images by hand, because a PDF template can carry values but not pictures; he reviews the draft; and a **save** is what turns it into a record, giving it its `TS-####` and its change-check at that moment. Nothing enters `car` or `enquiry` before a save, so the board, the counts, the section lists and the showroom need no filter to keep a draft out — they never see one. The record's own rules (a required field, a state, a valid amount) are enforced **when the draft is saved**, not when it is uploaded; until then a draft is allowed to be incomplete. A draft holds only what the file carried and what the owner put in it: nothing is inferred, defaulted or invented, and this layer's anti-fabrication rule applies to a draft exactly as it applies to a record. **The file carries the record's editable fields and nothing else** — for a car its fourteen details, for an enquiry its five (name, number, what they asked for, note, and the state) — and a state that a file names is applied **at the save**. A draft therefore sits in no state and occupies none, so a waiting draft never blocks a state's deletion; if the state a file names no longer exists when the draft is saved, the save asks the owner to choose.
**Why:** The owner's words — "it is saved in neo as draft, not real data". A draft is not a record: it has no code and no hash, it sits in no state and occupies none, it may hold half a record, and it may never be saved at all. Three things follow, and each was checked against the store as it is: a `TS-####` is given once and never reused, so a draft that took one would burn it forever; `car_photo` names a car, so a draft's images could not live there; and every existing read path trusts the real tables, so a draft inside them would have to be filtered out at each read point, where one forgotten filter puts unwritten data in a count or on a public page.
**Alternatives:** a `draft` flag on `car` and `enquiry` (rejected — puts unwritten records in the tables everything already reads, needs the filter everywhere, and burns a reference code); holding drafts only in the browser session (rejected — a batch of ten must survive a reload and be worked through over time); creating the record at upload and marking it hidden (rejected — that *is* writing the record, which the owner ruled out).
**Net:** one new table — the draft table, given its shape in **D16** — by a forward-only migration, and the real tables gain no column. **Ordering:** the migrations continue at `0020`, but the **state model (D15) migrates first**, so the draft table takes the next free numbers **after** it; a draft carries a state label, so the state model must be settled before the draft table exists.

### D14 — "Draft" means the upload's staged row, and nothing else (owner's word, 2026-10-14)
The owner calls the upload's staged row a **draft**, and that is the word's only meaning from here on. The older, different sense — a car that has no price or no photo and is therefore absent from the public pages — is the **listing gate**, and a car held by it is **not yet listed**. Both were called "draft" in earlier text; the rule in each case is unchanged, and only the second meaning's name changes, because two meanings of one word in the same layer is how a builder ends up implementing the wrong one (logged as a conflict in `tasks/TASK-004/task.md`).

### D15 — Two kinds of car state: primary (four, fixed, mandatory) and secondary (the owner's own) (owner ruling 2026-10-14)
**Decision:** A car's states come in two kinds. A **primary state** is one of exactly four, fixed and final: **Available, On Order, Landed, Sold**. **Every car sits under exactly one primary state** — it is not optional, and a car without one is not a valid car. A **secondary state** is *any state that is not one of those four*: the owner creates them himself, a car may carry **none or several**, and they exist for **his own tracking**. The primary state is what the **showroom** reads; a secondary state never appears on the showroom. One rule binds the two: **a car may have no secondary state, but it may never have a secondary state without a primary one.** D12 is untouched — the states are still labels, not stages, no order is enforced between them, and the owner may give a car any of them at any time. What D15 adds is that exactly one of the labels is **mandatory**, and only four values are allowed for it.
**Why:** The owner's words (2026-10-14) — "the client is the one that assigns a car landed … primary states are those ones that every car must be part … the rest are secondary states … a car can have more than one secondary state". One list was serving two jobs: the showroom needs a small fixed vocabulary it can build pages and counts on, while the owner needs room to invent his own tracking labels without those labels reaching the public pages. Splitting the list gives each job its own vocabulary, and turns "every car is somewhere in the showroom" into a fact rather than a hope.
**Alternatives:** one flat list where any state may be a car's state (rejected — the showroom would have to present a label the owner invented yesterday, and a car could sit under no state at all, which is the store's present weakness: `car.state_id` is nullable and `On the way`/`At port`/`Cleared` are publicly grouped as though a customer should care); a fixed set of four with no owner-created states (rejected — it removes the tracking he asked for).
**Consequences:** (a) **D6 is revised:** Sold is now a primary state a car sits under, not only a flag — the sale record still holds the money facts (price, date, profit), and un-marking a sale returns the car to a non-Sold primary state, logged. (b) The store's five car states split: **Available** and **Landed** are already two of the four; **On the way**, **At port** and **Cleared** are not among the four, so they become **secondary** — the customer sees the car as **On Order** while the owner tracks its stage privately; and **On Order** (until now only a showroom group, never a state) and **Sold** (until now not a car state at all, only a flag) are added as **primary states**. (c) A car's several secondary states need somewhere to live — a link between a car and the states it carries — so the schema this involves is **more than the single new table** the build handover had assumed. (d) **The showroom's three groups are three of the four primary states** — Available, On Order and Landed — so the showroom's grouping and the mandatory vocabulary now coincide, and **Sold is the one primary state the showroom never shows** (the owner's words, 2026-10-14). A landed car stays presented under Available as it is today, the "Landed this year" reading is unchanged (the Landed primary state carries the new-arrival flag), and *section* and *primary state* now name the same thing — **the specs still carry the older "section" vocabulary in places and have not been fully rewritten; that rewrite is pending** (stated here rather than assumed done). The one requirement that *contradicted* D15 rather than merely differing in wording — `specs/inventory`'s "Sold is a flag, not a state" — has been **rewritten, not deferred** (see D6). (e) **Not stated by the owner, and therefore left as they are:** whether the same two-kinds split reaches **enquiry** states. His words were about cars, so enquiry states keep their present single kind — freely created, ordered, renameable and deletable by the owner — until he says otherwise. (f) **A car's secondary states are kept when it is marked Sold** (owner ruling 2026-10-14, answering what D15 left open): only the **primary** state becomes Sold, so the car's own tracking labels stay attached to it, and un-marking returns the car to its previous primary state **with those labels intact** — nothing is cleared, so nothing has to be undone. (g) **The demo fleet still needs its mapping, and that is the next thing the store owes:** the 17 demo cars sit in the five present states, and once three of them become secondary, every car still needs a primary. The mapping the owner accepted (2026-10-14) keeps the showroom looking exactly as it does now — **Available → primary Available; On the way / At port / Cleared → primary On Order, with the old label kept as a secondary; Landed → primary Landed** — and adds **at least one car carrying a secondary label and one car Sold**, so both new behaviours are visible in the demonstration. The builder performs this mapping in the state-model migration and seed.

### D16 — The draft table's shape: one table, with the images as an ordered list on its own row (owner ruling 2026-10-14)
**Decision:** D13's one new table holds a draft in columns: `id`; `kind` (`car` | `enquiry`); `batch_id` (the drafts of one upload share it); `source_filename`; `source_asset_id` (the uploaded file, in Sanity); `values` (the record's editable fields, as jsonb); `image_asset_ids` (an **ordered** list of Sanity image references — index 0 is the cover); `state_label` (nullable — the state *name* the file named, resolved at the save); `is_demo`; and timestamps. **A draft's images live as an ordered list on the draft's own row, never in a second table** — D13 promised one new table, and a cover is a position, which a list carries natively.
**Why:** Nothing about a draft needs to be joined, queried by, or referenced from anywhere else: it is read by its own screen, saved once, and cleared. A second table would add a foreign key, a second write path and a second thing to keep in order, for no query it would serve. `state_label` is deliberately a **name, not a state id** — a draft sits in no state and occupies none (D13), so a waiting draft must not hold a live reference that would block a state's deletion.
**Alternatives:** two typed tables (`car_draft`, `enquiry_draft`) — rejected: it duplicates the whole shape per kind to gain nothing the `kind` column does not already give; a second `draft_image` table — rejected: it breaks D13's "one new table" and buys no capability.
**Where the owner works them:** "Create from file" appears on the office inventory and enquiry screens, the car template is downloadable there, and **every draft of both kinds is reviewed in one place, `/office/drafts`**. A draft carries the demo marker, so the wipe clears drafts with everything else.

### D17 — Our own session row is created lazily, with no webhook (owner ruling 2026-10-14)
**Decision:** The `session` row is created on the first office request that carries a valid provider session — an upsert keyed by the provider's session id on the unique column the schema already has — and `last_seen_at` is refreshed on the existing 5-minute cooldown. No sign-in webhook and no sign-in callback route exist.
**Why:** A provider-carried sign-in (D4) never tells our server that a sign-in happened, yet the application's own rules (the 7-day cap and the 12-hour idle limit) need a row of our own to run against. A webhook would mean a public endpoint plus a signing secret to store, rotate and monitor; a callback route would mean another unauthenticated surface. The lazy upsert needs neither, and the row it creates is the row the request is about anyway — the check and the creation are one act.
**Alternatives:** a `session.created` webhook (rejected — public endpoint plus a secret, for a single-owner product); a sign-in callback route (rejected — a new unauthenticated path, and one the provider's component does not take).

### D18 — A transient store failure becomes a retryable state, from one shared guard (owner ruling 2026-10-14)
**Decision:** Every server-side store read passes through **one shared guard**, and a transient failure — cold compute, a dropped connection, a timeout — is turned into a **clear, retryable state** by one shared component, with **route-level error boundaries** behind it. Guard, component and boundaries apply to **both** the office and the public showroom pages.
**Why:** The carried finding is that the first request after Neon scales to zero can return a 500 (D8's trade-off; recorded in TASK-004). One guard is one place to get right and one place to test, and it is what keeps truth 16 true: a blip must never become an error page and must never produce an invented figure. Per-page `try`/`catch` writes the same rule N times, and the first page that forgets it is the one the owner sees.
**Alternatives:** per-page handling (rejected — drifts, and nothing enforces it); the framework's default error page (rejected — it *is* an error page, which is the outcome the truth forbids, and it offers no retry).

### D19 — The two operational notices are read from setting rows (owner ruling 2026-10-14)
**Decision:** Storage-past-threshold and backup status are **setting rows the office only displays**: a `last_backup_at` value **written by the daily job** (D8 — TASK-006's work) and a storage-warning figure with a default of **4 GB**. No new table, and no live computation of storage from the image store.
**Why:** The job is what knows a backup happened, and one writer per fact is the rule this architecture keeps everywhere else. Computing storage live would put a Sanity call on an office page render — a failure mode traded for a number nobody watches by the second. Reading a row leaves the office's read path unchanged in kind.
**Alternatives:** compute storage live here (rejected — a remote call on a page render, for a number the job can write); drop the notice and call it a TASK-006 gap (rejected — the settings spec requires the notice, and the office can display a row today).

### D20 — The two leftovers are left alone: `activity_event` and `auth_attempt` (owner ruling 2026-10-14)
**Decision:** `activity_event` **gains nothing**: the writer records the action's `kind` and puts a car's `TS-####` reference in `subject`, and no new typed column is added. `auth_attempt` is **kept exactly as it is** — the daily job's 90-day retention rule on it (D8) survives, and it stays a harmless no-op, because a provider-carried sign-in (D4) never passes through our server and no attempt row is ever written.
**Why:** A new column needs a requirement that asks for it, and `kind` plus `subject` already carries what the activity feed shows — a typed column would be shape built ahead of a need, and shape is the expensive thing to change afterwards (this very revision is the lesson). For `auth_attempt`, removing it would mean a forward-only migration plus edits to `specs/media` and TASK-006's plan, and would gain no behaviour: the table is empty, nothing writes to it, and only the job that trims it reads it. **Leaving both alone is the cheaper truth.**
**Alternatives:** a typed `subject_id` column on `activity_event` (rejected — no requirement asks for it); dropping `auth_attempt` by migration (rejected — cost with no gain, and it would break the job's rule and two documents); narrowing it to successful sign-ins (rejected — the `session` row already *is* that record).

### D21 — The tap notice reads a "seen" watermark, and looking at it writes one (owner ruling 2026-10-16; reconciled from the developer's architecture deviation)
**Decision:** The badge counts **taps newer than the office's own mark**, not all taps. A one-row table `tap_seen` holds `seen_through` — the `at` of the newest tap the office actually rendered — and the count is `tap.at > seen_through`, with **every** tap new while no mark exists yet. The mark is taken by the store from a `tap` row that exists, **moves only forward**, and is written by a **POST Server Action fired when the full tap list is viewed**; the viewing itself is a GET and changes nothing. The glyph persists at zero and only the count circle clears, so the tap list keeps a permanent entry point (the topbar's rightmost icon and the sidebar's account row both link to it). `tap_seen` is **operational read-state** — not customer data, and not one of `setting`'s three keys — and it is the first new table since the state model; it relates to `tap` **by time, not by key**.
**Why:** The owner's ruling (2026-10-16) turned the notice from a statistic into a notification that clears when he reads it, and a watermark is the smallest thing that can hold "last looked at". This is the system's **first write-on-view**, so it gets named as a rule: *reads are effectless; acknowledging a read is a write.* Truth 3 survives intact, because the write is a POST and the *server* resolves the timestamp — a caller can neither make a read change data nor fast-forward the mark past a tap the store does not hold. It closes the two questions the design record left open: what the number counts (the taps since the last look, not an all-time total) and whether the glyph survives at zero (it does; only the circle clears). The all-time figure stays honest because `getOfficeTapCount()` is kept alongside `getNewOfficeTapCount()` — **both names are the ones the model wants** (every row / since the mark), so no rename.
**Alternatives:** a key in `setting` (rejected — the owner ruled a table over a key, and `setting` stays exactly its three keys); marking seen inside the GET that renders the list (rejected — that would make a read change data); an all-time count with a "clear" control (rejected — it invents a control the owner never asked for, when the view already knows it is the reader).

## Risks / Trade-offs

- **[Drafts accumulate and nothing removes them]** → Consistent with the standing ruling that the system never clears the owner's own work: an unsaved draft waits for him and is his to save or clear, and no job touches it. The one removal that survives is the job's own litter — an asset *no draft and no record* ever referenced (D8, specs/media). The opposite risk does not exist: a draft can never appear anywhere as a record, because it is not in the record's table.
- **[Cost leak is catastrophic and silent if wrong]** → The allow-list serializer is the only public data path (D2), plus a pre-handover automated check that greps every public response for cost-field names and fails the build; specs make it testable.
- **[Sanity bytes and Neon rows drift]** → Daily convergence job (D7) makes bytes and rows agree within 24 h; placeholder rendering covers the outage window.
- **[A leaked PDF reference is fetchable forever]** → References exist only in the database and authenticated office responses (D7); randomized filenames make guessing infeasible; the owner clears each file when he clears its import.
- **[Neon scales compute to zero on the free tier]** → The scheduled function fires at scale-to-zero, so the job never depends on a warm database; the office's first load after idle pays one cold start — accepted for a single-owner product.
- **[One-owner lockout via abuse control]** → The provider locks the account after 10 failed attempts, for a bounded period that clears itself (D4, owner ruling 2026-10-14), on top of its per-address rate limits. The lock is never indefinite and never needs support to clear, and a forgotten password is still recovered by a documented identity-provider operation (F2). The residual risk is the bounded window itself: for those minutes the owner cannot sign in — the price of the lockout, which he chose over the application's old delay schedule.
- **[Customer data lingers because nothing deletes it automatically]** → By owner ruling (2026-10-13) **nothing is ever deleted by the system on the client's behalf** — not customer data, not a car, not a file: the daily job only *reports* what is waiting to be cleared and the owner clears it, logged in activity. The opposite risk — the system deleting data he wanted — is designed out entirely. The reporting pass touches PII only, never cars or money; export exists first (office-settings); A4–A6 are owner-confirmed defaults to re-verify at the system-model pass.
- **[Planning prose and specs disagree in places]** → Ruling dates govern; `planning-close.md` is the arbitration record; known stale spots (e.g. `seed-content.md`'s global-rate line, and the rate columns in the business-logic and data-model plans, all superseded by the 2026-10-12 rate removal) are called out in tasks rather than silently patched here.
- **[Reference screens live outside the repo]** → Tasks treat `test-truespec-v2` as read-only visual truth; any behaviour conflict resolves to the specs, per planning-close's "rule wins over screen".
